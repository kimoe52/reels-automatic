# Jev 일회성 트렌드 수집 설계안

작성일: 2026-09-20

## 결론

이번 작업에서만 Jev를 사용한다. Jev를 영상 제작 앱이나 장기 파이프라인에 연결하지 않고, 공개 후보를 한 번 모아 코드로 최신성·반응·중복을 계산한 다음, Jev가 우리 채널의 릴스로 만들 만한 후보를 판단한다. 결과는 사람이 확인한 뒤 대본과 VLLO 편집 기준으로 고정한다.

흐름은 다음과 같다.

```text
허용된 공개 소스에서 후보 수집
        ↓
관찰된 사실 정규화
        ↓
최신성·반응·중복 계산(일반 코드)
        ↓
Jev 판단: 적합성·형식·재현성·근거·리스크
        ↓
사람 확인 / 유지 / 제외
        ↓
실제 사이트 화면 중심의 릴스 구성
```

Jev의 역할은 이번 배치의 마지막 세 단계다. 게시물의 존재, 게시일, 좋아요 수, 댓글 수처럼 정확히 읽어올 수 있는 값은 일반 코드가 처리한다. Jev에게 숫자를 보고 인기 순위를 다시 계산하게 하지 않는다.

## 왜 이 구조인가

TypeSafe는 Jev를 자연어와 애플리케이션 상태를 받아 typed decision, probability, confidence로 돌려주는 System One 모델로 설명한다. 공식 발표의 용도에도 분류·라우팅·스코어링·추출과 대규모 데이터의 특징화가 포함되어 있다. 따라서 `후보 수집 → 후보별 판단 → 점수 조합`이 `유행을 한 문장으로 요약해 달라`보다 제품 특성에 맞다.

Jev의 판단은 인터페이스를 보장하지만 사실을 자동으로 증명하지는 않는다. 그러므로 원본 URL, 캡처 시각, 게시일, 보이는 반응 수, 자막이나 캡션에서 확인한 문장을 모두 관찰 사실로 보관하고, `트렌드다`, `우리 채널에 맞다`, `재현할 수 있다`는 추론 필드로 분리한다.

## Jev에게 물을 판단

한 번의 질문에 모든 결정을 몰아넣지 않고, 같은 후보 상태에 독립적인 질문을 병렬로 보낸다. 질문 ID는 코드에서만 쓰고, 각 질문의 의미는 지시문과 기준에 온전히 적는다.

### 1. 채널 적합성: Noul

질문: 이 후보는 `AI·소프트웨어 도구를 실제 화면으로 보여주고, 사용자가 직접 촬영하지 않아도 재구성 가능한 릴스`에 적합한가?

판정 기준:

- yes: 화면 증거가 있거나 확보 가능한 공식 화면이 있고, 주제가 AI·소프트웨어·빌드 과정과 직접 연결됨
- no: 화면 근거가 없거나, 우리 채널의 주제와 무관하거나, 개인 촬영이 핵심이라 현재 제작 조건으로 재현하기 어려움

### 2. 형식: Choice

선택지:

- `result_first_demo`: 결과물을 첫 장면에 보여주는 사용 시연
- `problem_first`: 시청자가 겪는 문제를 먼저 제시한 뒤 해결 화면을 보여주는 형식
- `pov_reaction`: 개인 상황이나 반응을 훅으로 쓰고 실제 결과로 넘어가는 형식
- `tool_roundup`: 여러 도구나 기능을 짧게 비교하는 형식
- `build_log`: 입력·수정·배포 과정이 중심인 제작 로그
- `commentary`: 화면보다 주장이나 의견이 중심인 설명형
- `no_match`: 위 형식으로 안정적으로 분류할 수 없음

`no_match`를 반드시 포함한다. 후보가 빠진 선택지 안에서 억지로 하나를 고르게 하지 않는다.

### 3. 재현성: Score

점수 단계:

- 0: 실제 화면이나 입력 자료를 확보할 방법이 없음
- 1: 일부 화면은 가능하지만 핵심 결과를 직접 촬영해야 함
- 2: 공식 페이지 캡처와 허용된 브라우저 조작 녹화로 핵심 흐름을 재현할 수 있음
- 3: 실제 결과 화면이 이미 공개되어 있고, 같은 구조를 우리 소재로 바로 옮길 수 있음

이 점수는 `예쁘게 만들 수 있는가`가 아니라 `사용자의 직접 촬영 없이 설명을 증명할 수 있는가`를 평가한다.

### 4. 훅 명확성: Score

점수 단계:

- 0: 첫 화면에서 무엇을 보는지 알기 어려움
- 1: 주제는 보이지만 시청자 문제나 결과가 추상적임
- 2: 문제 또는 결과가 한 문장과 화면으로 이해됨
- 3: 결과·문제·사용 대상 중 하나가 첫 장면에서 즉시 보이고, 다음 화면의 이유가 생김

### 5. 근거 품질: Score

점수 단계:

- 0: 제목이나 재전달 문구만 확인됨
- 1: 게시물은 열리지만 영상의 핵심 장면을 확인하지 못함
- 2: 캡션과 영상 장면을 모두 확인함
- 3: 원본 화면, 캡션, 게시일, 필요한 기능의 공식 자료까지 서로 대조함

### 6. 과장·권리 리스크: Noul

질문: 이 후보를 그대로 따라 만들 때 확인되지 않은 성능 주장, 협찬·댓글 유도 맥락의 오해, 타인의 영상 재사용 문제가 생길 가능성이 있는가?

yes이면 자동 채택하지 않는다. `manual_review`로 보내고, 우리 영상은 원본을 복제하지 않고 사실이 확인된 화면과 자체 구성으로 다시 만든다.

## 점수 조합과 행동

아래 가중치는 시작값이지 보편적인 임계값이 아니다. 실제 게시 결과를 모아 조정한다.

```text
fit = 0.35 * channel_fit
    + 0.25 * reproducibility
    + 0.20 * hook_clarity
    + 0.20 * evidence_quality
```

행동 규칙:

- `risk = yes`이면 점수와 관계없이 `manual_review`
- `channel_fit = no`이면 `discard`
- `confidence < 0.70`이면 `manual_review`
- `fit >= 0.72`이고 `evidence_quality >= 2`이면 `shortlist`
- 그 외에는 `watchlist`

이 규칙은 Jev의 confidence를 전체 작업의 정답률로 해석하지 않는다. confidence는 해당 판단의 불확실성을 다루는 신호이며, 실제로 좋은 릴스가 되는지는 별도의 게시 결과로 검증한다.

## 트렌드 점수는 코드로 계산

후보가 유행하는지에 관한 신호는 Jev가 아니라 코드가 계산한다.

```text
trend_signal =
  0.35 * recency_decay
+ 0.25 * normalized_engagement
+ 0.20 * cross_source_repeat
+ 0.20 * format_growth
```

여기서 `cross_source_repeat`는 같은 훅이나 형식이 서로 다른 계정과 허용된 소스에서 반복되는지 보는 값이다. 동일 영상의 재게시를 여러 개의 독립 신호로 세지 않는다. 조회수가 보이지 않는 플랫폼은 null로 두고, 그 값을 0이나 추정치로 바꾸지 않는다.

결과 화면에는 `trend_signal`과 `jev_fit`을 따로 표시한다.

```text
유행 신호가 높음 + Jev 적합성 높음 → 이번 주 제작 후보
유행 신호가 높음 + Jev 적합성 낮음 → 관찰만, 억지로 복제하지 않음
유행 신호가 낮음 + Jev 적합성 높음 → 채널 고유 소재 후보
둘 다 낮음 → 제외
```

## Jev 릴스에 적용하는 첫 실험

이미 확인한 레퍼런스 5개를 후보 데이터로 넣고, 아래 세 형식을 비교한다.

1. `result_first_demo`: 오류가 난 작업 화면과 다음 행동 선택지를 먼저 보여준다.
2. `problem_first`: "Codex가 또 실패했는데, 다음에 뭘 해야 할까?"를 먼저 보여준다.
3. `tool_roundup`: 재시도·다른 AI·다른 툴·사람 확인을 한 화면에서 비교한다.

Jev가 고를 최종 형식은 단순한 인기 순위가 아니라 다음 조건을 만족해야 한다.

- 실제 선택지가 화면에 들어갈 것
- 프로그램이 판단 결과를 받아 다음 단계를 실행하는 구조가 보일 것
- 사용자의 직접 촬영 없이 캡처·도식·허용된 화면 녹화로 증명할 수 있을 것
- Jev의 실제 결과와 예시 UI를 혼동하지 않도록 표시할 것

현재는 TypeSafe Early Access 접근키가 없으므로 이 파일은 실행 가능한 API 연동이 아니라 판단 설계와 첫 평가 데이터셋이다. 키를 받으면 후보 5개를 한 번 호출해 `channel_fit`, `format`, `reproducibility`, `hook_clarity`, `evidence_quality`, `risk`의 분포와 confidence를 기록한다. 결과를 확정한 뒤에는 Jev 호출을 반복하지 않고, 선택한 형식과 편집 기준을 영상 제작에 사용한다.

## 일회성 키 사용

API 키는 저장소나 장기 환경변수에 넣지 않는다. 한 번 실행하는 로컬 셸에서만 `TYPESAFE_API_KEY`를 설정하고, 배치가 끝나면 셸을 닫거나 변수를 해제한다. `.env.local`을 만들더라도 이 임시 작업 폴더에만 두고, 결과 확인 후 키가 포함된 파일을 남기지 않는다.

## 출처와 제한

- TypeSafe 공식 홈페이지: Jev가 typed decision과 calibrated probability를 반환하고, 높은 confidence에서는 자동 실행하고 낮은 경우 검토로 보낼 수 있다고 설명한다.
- TypeSafe 공식 발표(2026-09-15): Jev를 구조화된 확률 판단 모델로 설명하고, 분류·라우팅·스코어링·추출·대규모 데이터의 특징화와 실시간 워크플로를 사용 사례로 제시한다.
- 공개 릴스의 반응 수는 조사 시점의 값이다. 조회수·완주율·저장 수는 이 설계에서 확인하지 못한 값이다.
